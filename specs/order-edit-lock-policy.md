# Order Edit Lock Policy

## 1. Overview

Currently, DineFlow prevents adding items to an order once its status moves beyond `SentToKitchen`. This is too restrictive — restaurant staff need to be able to add items to a running order at any point up until the customer has actually paid. The lock should only kick in when payment is confirmed (status `Paid`) or the order is closed (status `Closed`).

## 2. Goals

- Allow order item additions for every status from `Placed` through `Billed`.
- Block order item additions only when status is `Paid` or `Closed`.
- Surface the lock clearly in the UI so staff are not confused by a silent backend rejection.
- Keep the enforcement authoritative on the backend; the frontend mirrors it for UX only.

## 3. Scope

### In Scope

- Change the status gate in `OrderService.AddItemsAsync` from `{Placed, SentToKitchen}` to `{anything except Paid, Closed}`.
- Update the `EditOrderPage` to show a read-only view (disabled form + explanatory message) when the order is `Paid` or `Closed`.
- Update the "Edit" link visibility on `OrderCard` to hide when status is `Paid` or `Closed`.
- Update all related unit and integration tests.

### Out of Scope

- Changing status transition rules in `Order.TransitionTo` (the state machine is not modified).
- Allowing removal or quantity changes of existing order items (the system remains add-only).
- Modifying billing or payment flows.
- Changing who (roles) can edit orders.

## 4. User Stories

- As a **Waiter**, I want to add more items to a customer's order while it is being prepared, so that I do not have to create a second order for the same table.
- As a **Manager**, I want to add items to an order even after it has been served, so I can accommodate late additions before the bill is finalized.
- As a **Manager**, I want the system to prevent any item additions once the customer has paid, so the closed bill stays accurate.
- As a **Waiter**, I want the Edit button to disappear (or be disabled with a clear message) on paid/closed orders, so I am not confused by an unexpected error.

## 5. Functional Requirements

### FR-001: Relaxed Status Gate for Adding Items

The backend service (`OrderService.AddItemsAsync`) must allow item additions for any order whose status is **not** `Paid` and **not** `Closed`.

Allowed statuses: `Placed`, `SentToKitchen`, `Preparing`, `OutOfStock`, `Prepared`, `Served`, `Billed`.

Blocked statuses: `Paid`, `Closed`.

### FR-002: Backend Returns Informative Error for Locked Orders

When a request to add items is rejected because the order is `Paid` or `Closed`, the service must return `Result<OrderDto>.Failure(ResultError.Conflict, "Cannot add items to an order that has already been paid.")`.

The existing HTTP mapping (409 Conflict) is unchanged.

### FR-003: Frontend — Hide Edit Link on Paid/Closed Orders

`OrderCard.tsx` must hide the "Edit" link when `order.status` is `OrderStatus.Paid` or `OrderStatus.Closed`.

The existing role check (`Admin | Manager | Waiter`) is unchanged — both conditions (role check **and** status check) must pass for the link to appear.

### FR-004: Frontend — Read-Only State on EditOrderPage for Locked Orders

`EditOrderPage.tsx` must detect when the loaded order's status is `Paid` or `Closed` and render a locked state:

- The item-selection form (quantity inputs, submit button) is not shown.
- A visible banner/alert is displayed: _"This order has been paid and can no longer be edited."_
- The existing order summary (current items, status badge) is still visible for reference.

### FR-005: Consistency — `canEdit` Helper

Extract the editability rule into a single pure helper function so both `OrderCard` and `EditOrderPage` use the same logic:

```ts
// src/features/orders/orderUtils.ts  (new or existing file)
export function isOrderEditable(status: OrderStatus): boolean {
  return status !== OrderStatus.Paid && status !== OrderStatus.Closed;
}
```

Both components import and call this helper. No inline status comparisons.

## 6. Business Rules

- An order **may** receive new items as long as it has not been paid.
- An order in `Billed` status **may** still receive new items (the bill will need to be re-generated by staff — out of scope for this spec but expected workflow).
- An order in `Paid` or `Closed` status **may not** receive new items under any circumstance.
- Role-based access (Admin, Manager, Waiter only) is unchanged.
- The restriction applies regardless of the order channel (`DineIn`, `Takeaway`, `Zomato`, `Swiggy`, `Other`).

## 7. User Flow

**Happy path — adding an item to a Preparing order:**

1. Waiter opens the Order Dashboard.
2. Waiter finds an order with status `Preparing` and taps "Edit".
3. System opens `EditOrderPage` with the item picker enabled.
4. Waiter selects an additional item and submits.
5. System calls `PATCH /api/orders/{id}/items` — backend accepts (status is `Preparing`, not `Paid`/`Closed`).
6. System shows a success toast; the order card reflects the new item.

**Blocked path — attempting to edit a Paid order:**

1. Waiter opens the Order Dashboard.
2. Order with status `Paid` does **not** show an "Edit" link on its card.
3. If the waiter navigates directly to `/orders/{id}/edit` (e.g. via browser history):
   a. `EditOrderPage` loads the order.
   b. Page renders the read-only banner: _"This order has been paid and can no longer be edited."_
   c. No item-picker or submit button is shown.

## 9. API Requirements

No new endpoints. Only the service-layer guard changes.

### Existing endpoint (behavior change only)

```text
PATCH /api/orders/{id}/items
```

**Authorization:** `Admin`, `Manager`, `Waiter` (unchanged).

**Request body** (unchanged):

```json
{
  "items": [
    { "menuItemId": "uuid", "quantity": 1, "notes": "no onion" }
  ]
}
```

**Success response** (unchanged): `200 OK` with `OrderDto`.

**New failure case:**

| Scenario | Status | Body |
|---|---|---|
| Order status is `Paid` | `409 Conflict` | `{ "error": "Cannot add items to an order that has already been paid." }` |
| Order status is `Closed` | `409 Conflict` | `{ "error": "Cannot add items to an order that has already been paid." }` |

**Removed failure case:**

| Old scenario | Old status | Note |
|---|---|---|
| Status is `Preparing`, `OutOfStock`, `Prepared`, `Served`, or `Billed` | `409 Conflict` | **These are no longer blocked.** |

### Frontend

| Rule | Details |
|---|---|

## 13. Error Handling

| Scenario | Backend behavior | Frontend behavior |
|---|---|---|
| Add items to `Paid` order | `409 Conflict` with message | Toast error: display the server message |
| Add items to `Closed` order | `409 Conflict` with message | Toast error: display the server message |
| Add items to `Preparing` order | `200 OK` | Success toast (previously this was a 409) |
| Add items to `Billed` order | `200 OK` | Success toast (previously this was a 409) |

The frontend already handles `409` responses from `addItemsToOrder` as error toasts — no new error-handling code is needed beyond the UI locked state described in FR-004.

## 14. Non-Functional Requirements

- **No performance impact** — the status check is an in-memory enum comparison; no additional DB queries.
- **Audit log** — adding items to an order in `Preparing`/`Served`/`Billed` status follows the same audit trail as adding items in `Placed`/`SentToKitchen`. No audit changes needed.
- **Backward compatibility** — the API contract (endpoint URL, auth headers, request/response shape) is unchanged. Only the accepted status values widen.

**Given** an order with status `Preparing`

**When** an authorized staff member (Admin/Manager/Waiter) submits valid items via `PATCH /api/orders/{id}/items`

**Then** the response is `200 OK` and the items are appended to the order

---

### AC-002 — Adding items to a Billed order succeeds

**Given** an order with status `Billed`

**Then** the response is `200 OK` and the items are appended to the order

**Then** the response is `409 Conflict` with the message _"Cannot add items to an order that has already been paid."_

### AC-004 — Adding items to a Closed order is rejected

## 18. Implementation Notes

### Backend change (one line)

In `backend/DineFlow.Application/Services/OrderService.cs`, replace:

```csharp
// Current (line ~179-180)
if (order.Status != OrderStatus.Placed && order.Status != OrderStatus.SentToKitchen)
    return Result<OrderDto>.Failure(ResultError.Conflict, $"Cannot add items to an order with status {order.Status}.");
```

with:

```csharp
if (order.Status == OrderStatus.Paid || order.Status == OrderStatus.Closed)
    return Result<OrderDto>.Failure(ResultError.Conflict, "Cannot add items to an order that has already been paid.");
```

### Frontend — `isOrderEditable` helper

Create or add to `frontend/src/features/orders/orderUtils.ts`:

```ts
import { OrderStatus } from '@/types/enums';

export function isOrderEditable(status: OrderStatus): boolean {
  return status !== OrderStatus.Paid && status !== OrderStatus.Closed;
}
```

### Frontend — `OrderCard.tsx` change

The current `canEdit` check (line ~128):

```ts
const canEdit = role === UserRole.Admin || role === UserRole.Manager || role === UserRole.Waiter;
```

Must become:

```ts
const canEdit =
  (role === UserRole.Admin || role === UserRole.Manager || role === UserRole.Waiter) &&
  isOrderEditable(order.status);
```

### Frontend — `EditOrderPage.tsx` change

After fetching the order and before rendering the form, add:

```tsx
if (!isOrderEditable(order.status)) {
  return (
    <div>
      {/* order summary — existing markup */}
      <Alert variant="destructive">
        <AlertDescription>
          This order has been paid and can no longer be edited.
        </AlertDescription>
      </Alert>
    </div>
  );
}
```

### Test data seeding

Existing service tests use `_context.Entry(entity).Property("Status").CurrentValue = value` (or the equivalent) to bypass the private setter. Use the same pattern to seed orders in `Preparing`, `Paid`, and `Closed` states for the new test cases.
